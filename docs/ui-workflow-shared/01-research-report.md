# AI Food Diary 跨平台 UI/UX 设计基础研究报告

> 阶段：深度模式 · 仅做设计研究，不实现生产代码
>
> 研究结论区分：**事实证据**（来源或仓库可观察事实）、**设计推断**（由证据推导的建议）、**待验证假设**（需用户测试或产品数据确认）。

## 1. 结论摘要

AI Food Diary 应把“记录一餐”设计为全产品的最短闭环：**拍照/手动输入 → AI 生成可编辑草稿 → 用户确认 → 保存 → 当日反馈**。AI 不是替用户做不可逆决定，而是减少输入工作；食品名称、份量、烹调方式和营养估算必须可见、可修正，并明确标注为估算。

Web 与 Android 应共享品牌 token、信息命名、营养颜色语义和状态文案，但不共享布局：Web 适合可扫读的多栏概览、持久导航和同时比较；Android 适合单手操作、相机优先、底部导航/底部 Sheet 和渐进披露。当前仓库已有暖色专业基线和缓存优先/异步 AI 流程，下一步主要是统一“草稿—审核—保存”的状态模型，降低视觉噪声，并验证健康用户与健身进阶用户对信息密度的不同需求。

## 2. 仓库事实基线

1. **Web 导航现状**：`src/components/dashboard-nav.tsx` 将「飲食/健康/食物/設定」作为四个胶囊式顶层入口；激活态为琥珀色填充。该结构可保留为共享 IA 的基础，但 Web 还需要在“饮食”内部支持日期、餐次、营养趋势等二级结构。
2. **Web 视觉现状**：`src/app/globals.css` 使用暖米色背景、琥珀/橙/粉色环境光、玻璃卡片、Plus Jakarta Sans、圆角与 hover/渐变动效，并已有 `prefers-reduced-motion` 对环境动画和棱彩边框的处理。**推断**：品牌方向吻合“温暖专业”，但高饱和多色光晕、玻璃透明度和动态边框应限制在装饰层，不能承载关键文字、图表或状态语义。
3. **Android 主题现状**：`mobile/lib/theme/app_theme.dart` 已有暖色 light/dark palette；宏量营养素使用 protein sky、fat amber、carbs rose；状态色包含 success/danger/water；卡片圆角 20、输入字段 14、chip 全圆角。**推断**：这些可作为共享语义 token 的候选来源，不宜直接把 Android 色值未经对比度验证复制到 Web。
4. **Android 体验现状**：`mobile/lib/screens/dashboard_screen.dart` 已有饮食/健康/设置 tab、缓存优先加载、AI 分析完成 SnackBar、昨日总结和异步健康同步。**推断**：离线/弱网反馈与后台状态应成为设计系统的一等状态，而不是实现细节。
5. **产品现状**：README 说明 Web 与 Android 共用后端和版本号；能力包括 AI 餐点辨识、精确模式、昨日总结、常用食物/条码/营养标示、Health Connect 与隐私加密。

## 3. 外部参考与证据

### 3.1 AI 饮食记录与营养追踪搜索

- 搜索摘要一致指向：相机/照片应是显眼的记录入口；识别多个食物后需要展示可编辑建议；不能把 AI 估算直接当成最终事实。
- 参考方向：温暖专业、平静的健康 dashboard；象牙/石色背景、深橄榄或炭黑文字、柔和 terracotta/apricot 强调色。
- 可迁移模式：拍照优先但保留手动、相册、条码和营养标示入口；结果区分识别、修正、确认保存三个阶段。
- 不应照搬：只做大相机按钮而忽略无法拍摄或需要精确输入的用户。

### 3.2 跨平台健康/营养设计系统搜索

- 搜索结果建议：移动可用 Today、Log、Plan、Progress、Profile；Web 可用 overview、meals/nutrients、goals、trends 等持久结构。
- 可迁移模式：Web 采用持久侧栏与工作区；Android 采用底部导航或响应式导航。宏量营养素需要稳定语义色、文字标签与数值同时表达。
- 不应直接照搬：当前产品已有「飲食/健康/食物/設定」Web 结构与三项 Android tab，不能因外部模式而盲目增加一级入口。
- 相关规范线索：Android responsive navigation、WCAG 2.2、Health Literacy Online、Material navigation。

### 3.3 Mobbin 模式库

Mobbin 内容展示了 Home、Settings、Login、Account Setup、Profile，以及 Slider、Carousel、Sidebar、Bottom Sheet、Toast、Progress Indicator、Dialog、Tab、Button 等模式，并强调以完整 user journeys / flows 观察模式。

- 值得借鉴：Bottom Sheet 承载输入方式、份量编辑、常用食物选择；Dialog 用于删除等高影响操作；Slider 要搭配精确数字输入；空状态应提供下一步。
- 不宜照搬：复杂 carousel/onboarding 可能延迟首餐记录；模式库的价值主要在任务流程，不是视觉皮肤。

### 3.4 60fps.design 动效分类

内容按 bottom sheet、button、card、empty state、loading、progress、quick actions、recap、pull、search、spring physics、stagger、toast 等分类。

- 值得借鉴：AI 状态采用轻量进度说明；识别结果可低幅度 stagger；Bottom Sheet 采用克制 spring；保存成功用短时 Toast/SnackBar；空、载入、进度、快速动作优先于复杂特效。
- 不宜照搬：连续视差、全屏粒子、过度弹跳与持续漂浮卡片会降低健康工具可信度，并增加 Android 性能和无障碍风险。

### 3.5 Awwwards、Godly、Supahero、Pinterest

这些来源适合参考网页留白、层次、食物摄影情绪、渐变与模糊趋势，可用于品牌欢迎区、每日总结或空状态背景；不应把营销网站的满屏渐变、超大标题、滚动叙事直接搬入高频记录工作流。

### 3.6 reactbits.dev/magic-bento

抓取失败，页面依赖 JavaScript 渲染，未取得可验证组件内容。不能基于名称推断其适用于本产品。若后续重新验证，需检查响应式卡片层级、键盘/屏幕阅读器、`prefers-reduced-motion` 与性能。

## 4. 可迁移组件模式

| 模式 | 建议 |
|---|---|
| 主记录入口 | 首页突出“拍照记录餐点”，同时保留手动输入、相册、条码入口 |
| AI 结果 | 展示多个识别食物、份量、营养估算；每项可编辑，最后确认保存 |
| AI 状态 | 显示“识别照片 / 估算份量 / 等待确认”等阶段，不使用无限 spinner 掩盖进度 |
| Web 导航 | 保留「飲食/健康/食物/設定」作为一级候选，使用侧栏与二级页面结构 |
| Android 导航 | 入口少而稳定；适用时使用底部导航，局部任务使用 Bottom Sheet |
| 份量编辑 | Slider 负责快速调节，同时提供数字输入、单位和常用份量 chip |
| 营养摘要 | 热量作为主摘要；蛋白质/脂肪/碳水保持稳定语义色、文字和数值 |
| 目标进度 | 同时显示已摄取、目标、剩余；不要只依赖圆环 |
| 趋势图 | Web 展示较长范围与筛选；Android 优先近期趋势和结论 |
| 同步状态 | 显示 Health Connect 权限、最后同步时间、失败原因和重试/重新授权 |
| 空状态 | 说明原因并提供唯一主动作，如“记录第一餐”“连接 Health Connect” |
| Toast/SnackBar | 用于保存成功、同步完成等低风险反馈；关键错误需持久显示 |
| Dialog | 用于删除、覆盖等高影响操作，并明确后果 |

## 5. 品牌、色彩与信息密度建议

### 5.1 方向

共享 Design DNA 建议为：暖米色/象牙色背景，深橄榄或炭黑高可读文字，Amber/terracotta 作为主要行动色，protein/ fat/ carbs 作为稳定语义色，柔和圆角、弱阴影、有限玻璃效果。

### 5.2 色彩使用原则

现有 Mobile 已有 amber brand、protein sky、fat amber、carbs rose、success/danger/water；Web 已有暖米色背景、琥珀/橙色光晕和玻璃卡片。共享的是语义与优先级，不必强行复制每个表面色值。

优先级：
1. 文字和数值；
2. 数据语义色；
3. 品牌强调；
4. 装饰渐变和光晕。

色彩不能单独传达营养或状态。实际 token 必须在 Web 浅色、Android 浅色/深色和色觉异常场景下做 WCAG 2.2 对比度验证。

### 5.3 信息密度

采用“摘要优先、详情渐进披露”：大众用户先看到今日状态和下一步，进阶用户展开份量、目标差距、趋势和 AI 估算细节。Web 可承载比较、表格和更长趋势；Android 以单手快速记录、近期摘要和可展开详情为主。

## 6. 平台差异

### Web

- 持久侧栏或宽屏导航，保留稳定页面位置；
- 今日页面可同时呈现今日概览、最近餐点、目标进度与趋势摘要；
- AI 结果可用照片/识别对象与可编辑表单的左右分栏；
- 使用 hover、键盘焦点、URL 导航和响应式断点；
- 不直接复制 Android 底部 tab、全屏相机或连续 Bottom Sheet。

### Android

- 主要动作靠近拇指可达区域；
- 拍照入口优先，手动/相册/条码在明确 Bottom Sheet 选择；
- AI 编辑优先用分步页面或 Bottom Sheet，减少横向分栏；
- 触控目标、系统安全区、键盘弹出、弱网与缓存状态必须纳入设计；
- SnackBar 仅作低风险反馈，关键错误保留在页面内；
- 不把 Web 全部卡片压缩进单一长页面。

## 7. 应避免的问题

1. 把 AI 估算当事实：必须标注估算、支持字段级修正与保存前确认。
2. 只做漂亮总结：每个摘要提供可行动的下一步。
3. Web 与 Android 复制布局：共享 token、字段语义和业务流程，平台化承载方式。
4. 颜色过多：语义色、品牌色、渐变和图片需要明确优先级。
5. 用 Toast 隐藏关键错误：识别失败、同步权限、保存失败需持久且可恢复。
6. 过度游戏化或制造羞耻感：用“还差多少/可以补充什么”代替“失败/吃错”。
7. 忽略 reduced motion、键盘焦点、屏幕阅读器和触控目标。

## 8. 未决风险与验证建议

- Android 是否需要独立“食物”入口：任务测试常用食物、条码、营养标示的发现率。
- 相机入口是否足够显眼：比较首页 CTA、浮动按钮和 Bottom Sheet 的首餐完成率。
- AI 结果是否容易修正：使用混合菜、多人餐、遮挡和不同光线照片测试。
- 份量控件：比较 Slider、数字输入、快捷份量 chip 的组合。
- 玻璃卡片可读性：在浅色、图片背景、低亮度设备上进行对比度检查。
- Android 深色语义色：用真实记录、空/错状态和图表实测。
- 每日总结日期：验证用户是否能正确判断昨日/今日数据。
- Health Connect 权限拒绝：测试首次授权、部分授权、拒绝、撤销和重新授权。
- AI 等待：记录不同延迟下的放弃率、重复提交和误触。
- 两类用户信息密度：测试“简洁摘要 + 展开详情”与“默认完整数据”。

## 9. 结论

最稳妥的方向不是重做一套完全不同的风格，而是收敛现有基础：**暖米色 + 深色文字 + amber/terracotta 品牌强调 + 稳定宏量营养语义色 + 柔和圆角 + 有限玻璃效果；相机优先但不排除手动/条码/营养标示；AI 先建议、再修正、后确认；Web 强调概览/比较/管理，Android 强调快速记录/单手/即时反馈。**

当前最需要验证的不是色值细节，而是：用户能否快速完成第一餐记录、是否信任并能修正 AI 结果、两类用户是否都能在合适的信息密度下持续使用。
