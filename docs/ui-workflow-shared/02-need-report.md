# UI 需求分析报告

> 阶段：深度模式 · 后续形态、视觉、信息架构、交互、内容专家的权威输入
>
> 本阶段只产出设计文档，不修改生产代码。

## 一、产品定位

AI Food Diary 是一个跨 Web 与 Android 的 AI 辅助饮食记录工具，帮助用户以拍照或手动输入快速建立可修正的饮食记录，并通过营养分析、健康数据与每日总结形成持续反馈。

产品目标：
1. 降低记录门槛，让用户快速完成“输入/拍照 → AI 草稿 → 修正 → 确认保存”。
2. 建立可信的 AI 辅助体验：AI 减少输入，不替用户做不可逆决定。
3. 同时服务大众健康用户和健身营养进阶用户，采用默认简单、详情渐进展开。
4. 统一跨平台身份：共享品牌、色彩语义、字体层级、字段命名、状态语言和组件原则；不复制布局。
5. 建立可扩展的 Design DNA、状态模型、组件命名和验收规则。

非目标：不做医疗诊断或绝对准确的营养承诺；不在本阶段写生产代码；不强制 Web/Mobile 共用页面布局；不通过羞辱、连续打卡或过度积分做强游戏化；不自动保存未确认的 AI 结果；不把 Health Connect 作为饮食记录的前置条件；不将营销网站的强渐变、视差和玻璃效果直接复制到高频工作流。

## 二、用户与场景

### 大众日常健康用户

希望快速知道今天吃了什么、是否大致均衡，并得到简单、非评判式建议。障碍包括不愿逐项输入、不熟悉营养术语、担心 AI 误判、记录中断后难以恢复。需要显眼的记录入口、清楚的今日概览、可修正但不复杂的 AI 结果和失败时的替代路径。

### 健身与营养进阶用户

关注热量、蛋白质、脂肪、碳水、体重、活动消耗、目标差距和历史趋势。需要份量、单位、数据来源、精确编辑、常用食物、条码/营养标示和更高信息密度，但不接受不可修正的 AI 结果。

### 关键场景

手机单手记录餐点；在餐厅/家中/办公室/健身场所拍照；Web 桌面或平板查看长期趋势；无法拍照时用手动、常用食物、条码或营养标签；弱网查看缓存并稍后同步；首次打开查看昨日总结；连接或管理 Health Connect；修正混合菜、份量、烹调方式和包装食品误识别。

## 三、需求优先级

### P0 核心记录闭环

- 登录/注册、会话与恢复错误。
- 今日饮食概览：日期、餐点、总热量、营养摘要、待处理状态、空状态首要动作。
- 新增餐点：相机、相册/文件、手动记录；精确模式可选且说明成本。
- AI 分析：上传、识别、估算、待确认等阶段；可离开后找回任务。
- AI 草稿：食品名称、份量、单位、烹调方式/说明、热量、蛋白质、脂肪、碳水；每项可编辑、删除、新增、重试。
- 确认保存：明确“确认并保存”，取消/返回/重试/保留草稿/放弃；失败保留编辑内容。
- 每日总结：明确日期，区分事实、AI 推论、建议；短、具体、可执行、非评判；可再次找到。
- 共享 Design DNA：品牌、语义颜色、字体、间距、圆角、层级、图标、无障碍、组件命名、交互人格、状态语言。
- 跨平台状态模型：idle/input/uploading/analyzing/review/saving/saved/offline/error/permission-required/permission-denied/syncing/sync-failed/empty。

### P1 营养与健康

营养趋势、饮水、体重与活动消耗、Health Connect 同步、常用食物。必须区分手动与同步来源，显示日期/来源/更新时间，处理空数据/部分数据/权限拒绝，核心饮食记录不被同步阻塞。

### P2 食物资产、账号与隐私

条码扫描、营养标示、个人食物库、AI 设置、Google 绑定、隐私/数据控制、App 更新。所有高影响操作可逆或需明确确认；不暴露密钥；数据来源透明。

## 四、关键流程

1. 登录/注册 → 今日概览。
2. 今日概览 → 拍照/手动/相册/常用食物/条码入口。
3. 输入 → 上传 → AI 识别 → 估算 → 待审核。
4. 待审核 → 编辑食品/份量/单位/营养 → 重新分析或确认保存。
5. 保存 → 当日反馈；失败保留草稿并提供重试。
6. 每日总结 → 事实数据/建议 → 跳转相关餐点或趋势；关闭后可从历史再次打开。
7. 健康页 → 趋势/饮水/体重/活动 → Health Connect 授权、同步、失败、重试。
8. 食物页/记录流程 → 搜索、选择、创建、编辑、封存或删除食物。
9. 设置 → 账号、Google、AI、隐私、数据、更新。

Web 可使用键盘、浏览器上传、持久侧栏、左右分栏和多栏比较；Android 使用相机优先、Bottom Sheet、单列分步编辑、系统权限、安全区和返回手势。

## 五、共享与平台化边界

### 必须共享

品牌身份；色彩语义角色；营养字段含义；AI 草稿/确认/保存状态；交互人格与核心状态语言；字体层级原则；组件语义命名；空/载入/错误/同步/权限的核心含义。

### 必须平台化

页面布局；顶层导航承载；相机/上传/权限流程；Bottom Sheet、侧栏和弹窗的具体使用；键盘/触控/返回手势；图表密度；具体字号、间距、圆角和阴影落地值（可共享 token 角色但允许平台适配）。

## 六、约束

- Web: Next.js App Router + TypeScript；当前导航为 `src/components/dashboard-nav.tsx` 的「飲食 / 健康 / 食物 / 設定」；当前视觉为 `src/app/globals.css` 的暖米色、环境光、玻璃卡片、Plus Jakarta Sans 与 reduced-motion。
- Mobile: Flutter Android；`mobile/lib/theme/app_theme.dart` 已有 light/dark palette、amber brand、protein/fat/carbs、success/danger/water、card 20、field 14、chip 全圆角；`dashboard_screen.dart` 已有缓存优先、tab、AI SnackBar、昨日总结、异步健康同步。
- 隐私：README 说明 AES-256-GCM 字段加密与用户自有 AI key 机制；UI 不暴露敏感凭证，不把估算包装成官方医学数据。
- 无障碍：颜色不能是唯一信息载体；Web 支持键盘与可见焦点；Android 支持大触控目标、系统字体放大和减少动画；图表与营养语义同时提供文字/数值。
- 共享 token 的原则是共享语义角色，平台可适配具体值；共享业务状态，平台化承载方式。

## 七、待确认问题

优先待决策项：目标地区与语言、两端深色模式、Logo/品牌图形/字体资产、字体是否统一、Android 是否独立“食物”入口、是否提供简洁/进阶模式、AI 估算等级、图片保存策略、Health Connect 数据类型、健康数据手动修正、目标设定来源、AI key 暴露范围、Google 绑定语义、每日总结触发方式、食物删除与历史关系、单位、离线创建与失败草稿保留。

## 八、设计原则

1. 先完成记录，再展示分析。
2. AI 是草稿生成器，不是最终决策者。
3. 每一个状态都必须可发现、可理解、可恢复。
4. 共享语义，不强制共享布局。
5. 数据不能只靠颜色表达。
6. 默认简单，详情渐进展开。
7. 健康反馈中性、具体、非羞辱。
8. 视觉温度服务于可信度，不抢夺注意力。
9. 高影响操作要可逆或明确确认。
10. 无障碍从 token、字体、图表、焦点、触控目标、键盘和减少动画开始。
11. 数据来源和估算性质透明。
12. 以首餐完成、AI 修正/确认、失败恢复和双用户信息密度来验证设计。

## 九、建议成功指标

- 首次用户能在一次流程内完成第一餐记录。
- AI 草稿保存前 100% 经过用户确认。
- 用户能发现并完成一次 AI 结果修正，并理解估算值与确认值区别。
- AI 失败、无结果、离线、权限拒绝时仍能通过替代路径完成记录。
- Health Connect 拒绝不阻塞基础饮食记录。
- Web 键盘、焦点、对比度、固定层遮挡通过验收；Android 触控目标、安全区、返回、字体放大、减少动画通过真机验收。
- 大众与进阶用户都能完成“记录 → 修正 → 保存 → 查看反馈”。
