# 02-need-report.md

> 深度模式｜Web-specific UI/UX 需求分析报告
> 本报告供形态、视觉、信息架构、交互与内容专家作为后续设计的权威输入。本轮只分析 Web application，不设计原生 Android / Flutter / Mobile App，也不修改生产代码。

## 1. Product Positioning｜产品定位

### 1.1 一句话定义

AI Food Diary 是一个桌面优先、响应式的 AI 辅助饮食与健康记录 Web 工作台，帮助用户完成「记录餐点 → 检查 AI 草稿 → 修正 → 确认储存 → 回顾趋势」的完整闭环。

### 1.2 产品类型与阶段

- **类型**：健康生活工具 / 数据管理工作台
- **阶段**：既有 Web 产品的结构重组与体验升级，不是全新产品
- **目标平台**：桌面 Web 优先，同时支持平板 Web 与移动 Web
- **非目标**：医疗诊断、治疗建议、绝对精确的营养判断、社交与强游戏化

### 1.3 用户问题

1. 逐项输入餐点成本高，用户容易放弃记录。
2. AI 估算可能不准确，用户需要知道哪些内容是推测值，并能轻易修正。
3. 今日饮食、历史记录、健康指标与我的食物目前分散在不同功能中，缺乏连续工作流。
4. 长期数据需要高信息密度，但不能变成难以扫描的数据墙。
5. AI 分析、储存、同步、离线与多装置冲突的状态容易被混淆。
6. 保存失败或网络中断时，用户担心已输入内容消失。
7. 热量、体重与健康指标容易产生焦虑，文案和颜色不能使用羞耻或评判性表达。

### 1.4 产品价值主张

- **记录低负担**：照片、文字描述、手动输入与常用食物都能进入同一记录流程。
- **AI 可审阅**：AI 只产生可编辑草稿，用户确认后才成为正式饮食纪录。
- **资料可恢复**：错误、离线、同步失败和冲突都必须提供明确的下一步。
- **摘要优先**：大众用户先看到今天最重要的结论；进阶用户可展开份量、营养值、来源和历史趋势。
- **温暖可信**：以台湾繁体中文沟通，不医疗化、不评判用户，不把饮食表现转化为羞耻感。
- **跨平台语义一致**：保留共享设计基础的色彩角色、字体、字段、状态和品牌身份；Web 采用自己的信息架构与互动方式。

### 1.5 仓库事实与兼容约束

本仓库没有 `web/` 目录，Web 事实来源为 `src/app/` 与 `src/components/`。

- 技术栈为 Next.js App Router + TypeScript，根目录 `package.json` 版本为 `0.70.0`。
- `src/app/dashboard/layout.tsx` 目前包含认证保护、品牌 Header、`max-w-3xl` 窄容器和导航。
- `src/components/dashboard-nav.tsx` 目前使用「飲食 / 健康 / 食物 / 設定」四项玻璃胶囊顶栏。
- `src/app/dashboard/page.tsx` 已有日／周视图、日期切换、热量、宏量营养素、净热量、饮水、餐点记录、周营养回顾和每日总结。
- `src/components/meal-capture-form.tsx` 已有照片、文字描述、手动输入、拖放、多图片、精确模式、营养标示、条码、常用食物、品牌搜寻、AI 分析、编辑确认与保存错误处理。

### 1.6 Web 信息架构需求

目标 Web 壳层应支持：

```text
全域 Web Shell
├── 持久导航
│   ├── 饮食
│   │   ├── 今日
│   │   ├── 历史
│   │   └── 待确认／草稿
│   ├── 健康
│   │   ├── 健康概览
│   │   ├── 营养趋势
│   │   ├── 饮水
│   │   └── 体重／活动
│   ├── 食物
│   │   └── 我的食物
│   └── 设置
├── 顶部辅助区
│   ├── 当前页面标题与路径关系
│   ├── 搜寻
│   ├── 状态中心入口
│   ├── 主题或使用者操作
│   └── 必要的日期／筛选控制
└── 主工作区
    ├── 摘要与 KPI
    ├── 相关指标
    ├── 餐点、表格或图表
    └── 可选详情抽屉／辅助面板
```

要求：

- 桌面 Web 采用侧栏作为主要领域导航；当前四个领域命名应保留。
- 主工作区遵循「顶部摘要 → 中段相关指标 → 底部详情或管理内容」。
- 卡片用于摘要与状态；表格用于比较、筛选与批量管理；抽屉或详情页用于单笔深入查看。
- 不因桌面密度而重复显示同一资料。
- 当前 `max-w-3xl` 只能继续用于窄表单或文字详情，不能限制整个桌面工作区。
- 平板应允许侧栏收起为紧凑导航或抽屉；辅助面板应转为抽屉或下移。
- 移动 Web 应改为单栏；表格保留优先字段，详情进入详情页或抽屉，不得强行缩小成无法阅读的多栏表格。
- 所有主要操作必须有可见入口，不能依赖 hover 或隐藏手势。

## 2. Target Users / Personas｜目标用户与角色

### 2.1 大众日常健康用户

- **目标**：快速知道今天记录了什么，获得简单且不带评判的下一步建议。
- **使用频率**：每日或每周数次。
- **主要任务**：快速记录一餐、检查 AI 是否大致理解餐点、查看今日热量/饮水/餐点数量、失败时改用手动记录。
- **主要障碍**：不熟悉热量与宏量营养素、不想填写太多字段、担心 AI 误判、遇到错误时不知道资料是否还在。
- **体验要求**：首要 CTA 明确且单一；默认摘要简单；AI 草稿边界清楚；不要求先连接健康资料；不使用「超標、失敗、吃錯」等羞辱式词汇。

### 2.2 健身／营养进阶用户

- **目标**：精确管理热量、蛋白质、脂肪、碳水、份量、历史趋势与资料来源。
- **使用频率**：每日多次，常在桌面 Web 上进行回顾与整理。
- **主要任务**：修正 AI 食物与份量、查看每日/每周/长期趋势、管理常用食物/条码/营养标示、比较目标与实际、编辑历史餐点并重复使用资料。
- **主要障碍**：AI 估算不透明、数据无法批次处理、过度简化、状态/来源/更新时间不明确。
- **体验要求**：桌面高密度但可扫描；支持表格、筛选、排序、批次动作与键盘；可编辑原始 AI 结果；显示资料来源、更新时间与估算性质；营养分类色不表示好坏。

### 2.3 低频管理角色

系统包含管理员设置、AI 服务设定、版本与资料管理能力，可能存在低频管理角色。

- **主要任务**：管理注册开关、AI 服务设置、Google 绑定、版本资讯或资料整理。
- **要求**：管理员能力不干扰一般工作台；高影响操作独立分组、明确确认并可恢复；管理员入口是否持续保留待确认。

### 2.4 共同路径与差异

共同路径：

```text
登入 → 今日饮食 → 记录餐点 → AI 草稿／手动确认 → 修正 → 确认并储存 → 查看今日反馈
```

大众用户关心「今天是否有记录、下一步做什么」；进阶用户关心「数值是否可解释、来源是什么、如何比较与批次管理」。两者不拆成两套产品模式；默认摘要简单，详情提供进阶深度。

## 3. Jobs To Be Done｜用户待完成任务

| JTBD | 触发情境 | 用户需要完成的结果 |
|---|---|---|
| 快速记录一餐 | 吃完饭、在餐厅或工作中 | 不需逐项输入，也能建立一份待确认餐点草稿 |
| 验证 AI 是否理解正确 | AI 分析完成后 | 清楚知道哪些是 AI 估算，并能修改食物、份量与营养值 |
| 正式保存资料 | 用户确认草稿后 | 明确区分「AI 完成」与「已储存」，确认后才写入正式记录 |
| 在 AI 失败时继续记录 | 图片模糊、服务错误或无法辨识 | 保留已有输入，并能改用描述或手动记录 |
| 回顾今天的饮食 | 一天中任何时间 | 看到餐点数量、热量、宏量营养素、饮水与待处理项目 |
| 比较历史趋势 | 每周或每月回顾 | 通过日期、周视图、趋势和表格理解变化，而不是只看到单日数字 |
| 管理可重复使用的食物 | 经常吃相同食物或包装食品 | 搜索、收藏、编辑、封存、还原与批次整理我的食物 |
| 处理同步与资料问题 | 网络不稳定、多装置编辑或健康资料过期 | 知道资料现在在哪里、是否已同步，以及下一步如何恢复 |
| 管理个人设定 | 初次使用或资料变化时 | 更新个人资料、目标、AI 服务、连接与资料控制，不阻塞基础记录 |
| 使用无障碍操作完成任务 | 只使用键盘、辅助技术或触控设备 | 不依赖 hover、颜色或鼠标完成记录、编辑、储存和恢复 |

## 4. Key User Scenarios｜关键用户场景

### 场景 1：首次登入并完成第一笔饮食纪录

- 进入今日饮食，空状态提供唯一主要「记录饮食」入口。
- 选择照片、描述或手动，进入 AI 草稿或确认表单。
- 个人资料、Health Connect 或 AI 高级设置不是第一餐的前置条件。
- 用户能理解第一笔资料是草稿还是正式纪录；空状态、分析失败和手动替代路径均可完成。

### 场景 2：照片记录与 AI 草稿审核

- 现有支持最多 5 张图片、单张 6MB 限制、拖放、精确模式和全屏确认。
- 上传中、分析中、分析完成、分析失败必须区分。
- 分析完成显示「AI 估算・待确认」；用户修改显示「已由你修改」。
- 重新辨识不得无声覆盖用户修改；保存失败保留照片、描述、草稿项目和修改；重复储存不得产生重复餐点。

### 场景 3：描述/手动替代照片

- 描述模式说明食物与大致份量；手动模式可直接输入食物、份量、热量和宏量营养。
- 手动记录不应被误认为 AI 验证；AI 失败保留原始描述和字段。
- 至少一项有效食物名称；错误就近显示并有整体错误摘要。

### 场景 4：查看、修正或重复历史餐点

- 编辑状态与已储存状态明显区分；离开有未储存修改时提醒。
- 删除说明影响范围；「再記一次」说明产生新餐点而非修改原记录。
- 无照片、单张、多张照片及营养值不完整都能正常查看。

### 场景 5：桌面查看今日与每周营养趋势

- 首屏显示日期、热量、宏量、饮水与待处理项目。
- 日／周、日期切换和筛选可恢复；周视图区分每日值与周平均。
- 图表有文字/数值/表格替代；缺少 Health Connect 消耗时不伪造净热量。

### 场景 6：查看健康资料与同步状态

- Web 显示健康资料、来源、最后更新时间和过期状态；不设计浏览器直接授权 Health Connect。
- 尚未同步、无资料、过期、同步失败不能混为一谈；Health Connect 拒绝不影响饮食记录。
- 健康指标不得呈现为医疗诊断；当前临床式 `good/warn/bad` 语义需重新确认。

### 场景 7：整理我的食物

- 桌面使用语义表格；支持搜索、筛选、排序、结果数量、收藏、条码、可能重复、资料不完整、封存。
- 批量封存前显示选取数量和影响范围；冲突提供使用/更新/还原/另存等动作。
- 移动 Web 保留名称、份量、关键营养值和主要动作，其余进入详情。

### 场景 8：保存失败、离线或发生冲突

- 保存失败显示「草稿仍保留」与重试；离线不伪装服务器已储存。
- 待同步、同步失败、冲突分开表达；冲突不静默覆盖；状态中心列出对象、日期、更新时间、状态、CTA。
- 局部 panel 失败时其他 Dashboard 内容仍可用。

### 场景 9：键盘与辅助技术完成核心流程

- `Ctrl/Cmd+K` 搜寻；`N` 新增且输入框聚焦时不触发；`Esc` 关闭或确认未保存。
- Dialog/Drawer 焦点进入、循环、关闭回触发元素；首个错误字段获焦点；核心动作不依赖 hover。
- 图表、颜色、图标和状态提供文字等价信息。

## 6. Required States｜必须支持的状态与边界

统一状态：`idle` 尚未开始、`input` 输入中、`captured` 已接收、`uploading` 上传中、`analyzing` AI 分析中、`review` 待确认、`review-unsaved` 未储存修改、`saving` 储存中、`saved` 已储存、`offline` 离线、`pending-sync` 待同步、`error` 操作未完成、`permission-required` 需要授权、`permission-denied` 尚未授权、`syncing` 同步中、`sync-failed` 同步失败、`empty` 尚无资料、`conflict` 已有其他更新。

不可混用：AI 完成 ≠ 餐点已储存；本机保留 ≠ 账号已储存；账号已储存 ≠ 已同步；没有健康资料 ≠ 拒绝授权；筛选无结果 ≠ 系统没有资料。

- **认证**：初始载入、登入/注册失败、会话过期、网络失败、成功导向。
- **今日饮食**：无纪录、部分/完整纪录、目标不足、无消耗数据、局部失败、无效日期。
- **新增餐点**：空白、输入、文件验证、非图片、6MB/5张上限、上传、分析、无法辨识、AI 未设定、完成。
- **AI 审核**：待确认、用户修改、重新分析、失败、空项目、保存中/成功/失败、离开未保存。
- **餐点详情**：无/单张/多张照片、编辑验证、删除确认/失败、重复记录成功/失败。
- **历史/趋势**：骨架、无资料、无筛选结果、日期无效、部分无数据、图表失败、过期。
- **健康**：未连接、已连接无资料、今日无资料、过期、部分同步、同步中/失败、来源未知。
- **饮水**：无纪录、目标不足、新增/删除失败、目标无效、离线待同步。
- **我的食物**：初次无资料、无搜索结果、分类无资料、封存、不完整、重复/条码冲突、批量部分失败、载入失败。
- **设置**：载入、字段错误、未保存、保存中/成功/失败、AI 未设定、Google 成功/失败。
- **状态中心**：待确认、处理中、待同步、失败、冲突、完成、无待处理、载入失败。

内容区优先骨架，离散动作使用 spinner；AI 显示阶段性文字；重要错误不得只放 Toast；保存失败保留全部输入；局部失败不打垮整个 Dashboard；错误说明发生什么、资料是否保留、下一步是什么。

Dialog/Drawer：焦点进入、键盘移动、Esc 关闭、dirty 先提示、关闭回焦触发元素、小屏滚动不遮挡；删除/封存/另存/冲突覆盖须确认。hover 只作辅助；触控 Web 至少 48px。

- P0 测试至少 80% 用户第一次完成「登入 → 今日 → 新增 → AI/手动 → 修正 → 确认并储存」；回访用户照片记录到储存目标约 90 秒内，首次用户约 3 分钟内。

## 8. Assumptions / Risks / Open Questions

### Assumptions

1. 现有 `/dashboard` 路由继续兼容；不强制迁移 URL。
2. 日/周视图、日期筛选、现有 API 可作为历史/趋势基础。
3. Web 读取 Health Connect 已同步资料，不在浏览器直接授权。
4. 离线/待同步/冲突是体验要求，但当前代码未证明已有完整本地同步引擎。
5. 台湾繁中，时区/单位以用户设定为准；SavedFoods 封存不影响历史餐点。
6. 相片、饮食、体重、健康是敏感资料；glass 仅作有限品牌层。

### Risks

- AI 信任：过强完成感或精确数字让用户跳过确认。
- 健康焦虑：红色、目标评分、`GOOD/OK/LIMIT` 可能变成道德评价。
- 资料一致性：直接 fetch/即时刷新未证明离线、冲突、幂等已完整支持。
- 高密度：过多变成数据墙，过少无法满足进阶用户。
- 响应式：AI 双栏、图片、多字段、表格在平板/移动易溢出。
- 深色主题：当前 `color-scheme: light`，需重做表面、边框、图表、状态对比。
- 无障碍：当前 Dialog、按钮、图表尚未证明完整焦点/名称/文字替代。
- 隐私：相片、饮食、体重、健康与 AI 设定需明确保存与第三方传送。
- 范围膨胀：条码、品牌、健康、管理员、Google、离线、导出挤压核心闭环。
- 非医疗误导：BMR/TDEE/BMI/生命征象不可用诊断式状态表达。

### Open Questions

1. URL：保留 `/dashboard` 内扩展、新增 `/app/*` 转址，或仅视觉侧栏；建议先保留旧路径。
2. 历史：延续 `/dashboard?date=&view=`、独立历史页，或两者并存。
3. Web 离线：仅缓存读取、本机草稿稍后同步，或完整离线；建议先定义明确草稿保留。
4. 深色：跟随系统、手动、系统默认且可覆盖。
5. AI 评分：改为资料完整度/信心等级、保留非评判提示、或移除食物评价而只留估算说明。
6. AI 字段：食物/份量/单位/营养全可编辑，或营养仅由重分析产生，或可编辑但显示来源。
7. 健康展示：仅活动/体重/睡眠/饮水、全部指标、或依权限/资料类型筛选。
8. 健康更新时间/过期规则、每日总结触发、照片与 AI 资料保留政策。
9. 目标来源：用户输入、系统计算，或并存但明确来源。
10. 时区、日期和单位策略；我的食物永久删除规则；设置/管理员可见范围。
11. 移动 Web 支持查看/简单记录、完整照片/描述/手动/AI 审核，或仅作原生 App 补充入口。
