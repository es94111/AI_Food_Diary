# Quickstart: 廠牌食品營養標示搜尋

驗證本功能的三個使用者故事（P1/P2/P3）與關鍵 edge case 是否如 spec.md 所述運作。對應 `data-model.md` 的欄位與 `contracts/brand-search-api.md` 的端點。

## 前置需求

1. 已依 `.env.example` 設定好基本環境（`DATABASE_URL`、`ENCRYPTION_KEY`、`REDIS_URL` 等），並已套用本功能新增的 Prisma migration（`prisma/schema.prisma` 的 `SavedFood.encBrand`）：
   ```bash
   npm run prisma:migrate
   ```
2. 已設定 `TAVILY_API_KEY`（或研究決策中選定的替代搜尋供應商金鑰）。
3. 測試帳號已在「使用者設定 → AI 設定」完成 AI 供應商設定（OpenAI／Gemini／相容端點皆可），沿用既有 AI 功能的設定方式。
4. 開發伺服器已啟動：`npm run dev`。

## 情境 1（P1）：輸入廠牌與品項，取得候選並存入我的食物

1. 登入後進入記錄一餐、新增食物項目的畫面（`manual` 分頁，與「上傳營養標示照片」同一位置）。
2. 分別輸入廠牌（如「光泉」）與品項名稱（如「保久乳」），觸發搜尋。
3. **預期**：30 秒內顯示 AI 整理出的候選營養標示（含熱量／蛋白質／脂肪／碳水化合物），且畫面標示此為 AI 估算值（FR-006）。
4. 確認資料無誤後送出。
5. **預期**：前往「我的食物」（`/dashboard/foods` 或新增食物的常用清單）可看到新紀錄，其建立來源顯示為「品牌搜尋」（`source = "BRAND_SEARCH"`），且 `brand` 已正確填入。
6. 重複步驟 2–4，但這次故意修改候選中的某個數值後再送出。
7. **預期**：「我的食物」中該筆紀錄的數值是使用者修改後的值，而非原始 AI 判斷值。

對應：Acceptance Scenarios 1–3、FR-001~FR-006、FR-009、FR-010、FR-013、SC-001。

## 情境 2（P2）：多筆候選時列出清單供選擇

1. 輸入一個已知有多種包裝規格或口味的廠牌與品項名稱（例如同品牌不同容量的飲品）。
2. **預期**：系統列出多筆候選（含可辨識的包裝規格／口味差異，最多 5 筆），不自動選定其中一筆。
3. 點選其中一筆候選。
4. **預期**：畫面才顯示該筆對應的營養標示供確認（未選擇前不顯示任何一筆的完整數值確認畫面）。

對應：Acceptance Scenarios（User Story 2）、FR-004。

## 情境 3（P3）：查無結果時的替代入口

1. 輸入一個查不到公開營養標示的虛構品牌與品項（如「測試廠牌 XYZ999」／「不存在的品項 ABC」）。
2. **預期**：畫面顯示查無結果訊息（對應 `candidates: []`），並提供切換至「拍照上傳營養標示」或「手動輸入」的明確入口。
3. 點擊該入口，改用手動輸入方式完成新增食物。
4. **預期**：可依既有既定流程正常完成，不受本次搜尋失敗影響。

對應：Acceptance Scenarios（User Story 3）、FR-007、SC-005。

## Edge Cases 驗證

| 情境 | 操作 | 預期結果 |
|---|---|---|
| 只填廠牌未填品項 | 只輸入「光泉」，嘗試觸發搜尋 | 系統提示需要填寫品項名稱，不觸發搜尋（FR-001） |
| 只填品項未填廠牌 | 只輸入「保久乳」，嘗試觸發搜尋 | 系統提示需要填寫廠牌，不觸發搜尋（FR-001） |
| 候選缺漏欄位 | 選用一筆來源不完整的候選（如缺脂肪數值） | 該欄位留白／標示未知；未補齊前送出按鈕為 disabled（FR-005、FR-008） |
| 搜尋服務逾時／未設定 | 暫時移除 `TAVILY_API_KEY` 後重試情境 1 | 顯示明確錯誤訊息，且未寫入任何「我的食物」紀錄（FR-011） |
| 疑似重複（FR-012） | 先透過品牌搜尋存入一筆「光泉」＋「保久乳」，再次以相同廠牌＋相似品項名稱搜尋並嘗試存入 | 送出時出現重複提示（`409 DUPLICATE_FOOD`，`reason: "brand"`），可選擇使用既有紀錄或仍建立新紀錄 |
| 未送出離開 | 開啟候選確認畫面後直接關閉，不送出 | 「我的食物」未新增任何未確認的紀錄（SC-004） |

## SC-002 驗證程序（常見品牌命中率 ≥85%）

SC-002 要求「對於台灣市售常見品牌包裝食品的抽測查詢，至少 85% 能成功找到對應的候選營養標示」。由於專案未設置自動化測試框架，以下列固定樣本清單作為可重現的人工驗證程序（對應 tasks.md T026）：

1. 依序對下列 20 組「廠牌／品項」執行情境 1 的搜尋步驟（步驟 1–3，不需送出存入），記錄是否回傳至少 1 筆候選（`candidates.length >= 1`）：

   | 15 | 義美 | 鮮奶 |

2. 命中率 = 命中筆數 ÷ 20。**預期**：命中率 ≥85%（即 20 筆中至少 17 筆有候選）。
3. 未命中的品項需記錄下來（品牌／品項名稱、查無結果或錯誤訊息），供後續調整 `src/lib/web-search.ts` 的查詢字串組成方式或 `analyzeBrandSearchCandidates()` 的判斷邏輯。
4. 樣本清單如隨時間出現下架／改版等干擾（找不到是因商品本身已停產而非功能缺陷），可等比例替換為其他台灣市售常見品牌包裝食品，並在驗證紀錄中註明替換原因。

對應：SC-002。
